Индексы - это дополнительная структура данных, которая создается поверх таблицы и хранит отсортированную копию значений одного или нескольких столбцов и указатели на соответсвующие строки в таблицах. Индексы позволяют СУБД находить данные без полного перебора всей таблицы.
Индекс это всегда trade-off между скоростью чтения и записи. А также индексы занимают место в БД

B-Tree сбалансированное дерево. Эффективен при высокой селективности в индексируемой колонке. Селективность это отношение уникальных значений в столбце к общему количеству значений в этом столбце. Чем выше доля уникальных значений, тем выше селективность. Для повышения селективности нужно формировать индекс по нескольким колонкам
Эффективно для использования:
операторов сравнения ( < > = <= >=)
диапазоны
сортировки
проверки на Null
При формировании индекса по нескольким столбцам работает правило левого префикса. Например, индекс по столбцам А+В+С будет работать по А, А+В, А+В+С, не будет работать по В или С. А+С будет работать в PG 13 частично через Skip Scan

При низкой селективности можно создать частичный индекс, т.е. проиндексировать только те слобцы, которые удовлетворяют условию where. Либо формировать индекс по нескольким столбцам

2. Hash - имеет струтуру хэш таблицы. При формировании такого индекса PG вычисляет хэш-функцию от значения индексируемой колонки и сохраняет пару: ключ - это хэш, а значение - это ссылка на соответсвующую строку. Эффективен для точного поиска по уникальным значениям, которые представляют длинные строки (например JWT-токен, url). B-Tree хранит всю строку, а Hesh только хэш.

3. GIN - инвертированный индекс, который для каждого уникального элемента хранит список ссылок на строки, в которых он встречается. Эфективен для поиска в данных, которые имеют составную структуру, а запросы нацелены на поиск отдельных элементов в этих струтрурах (JSONB, ARRAY, полнотесктовый поиск). Поиск по данному идексу очень быстрый, но мы платим высокую цену для операций встравки и место на диске. Т.к. при изменении одной строки СУБД обновляет индекс для всех элементов внтури этой структуры.

Что делать с индексами в высоконагруженном приложении (high-load система)?
1. Аудит индексов через pg_sta_user_indexes (убираем неиспользуемые и дубли)

2. Возможно кикие-то индексы нужно реализовать частичными

3. Для таблиц с частым обновлением Update можно настроить параметр fillfactor (например 80-90%), чтобы обеспечить возможность обновления HOT updates. Это позволит PG обновлять строки без модификации индекса, если индексируемые колонки не меняются.
